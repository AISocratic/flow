19Installation

One line, pasted into Claude Code. The agent does the rest.

Flow installs by instruction, not by package manager. There is nothing to download and no dependency to add. You paste a single line into a coding agent already running in your project, and that agent performs the installation itself — reading the repository, creating the skill, mounting the board, building the dashboard, and proving it works before it stops:

claude "Install Flow in this project: read github.com/AISocratic/flow, then follow install.md top to bottom."

The same line works with any other coding agent:

codex "Install Flow in this project: read github.com/AISocratic/flow, then follow install.md top to bottom."

How it works

There is no Flow package to add and no Flow runtime to run. The repository carries an install.md written for the agent rather than for a human, and the agent executes it as a sequence of checked steps:

  • Read the repository. The agent fetches the repo, reads install.md, and reads the spec it references before changing anything.
  • Check preconditions. A git repo, a clean working tree, and — if you are integrating rather than running standalone — an existing authenticated admin area.
  • Cut a snapshot branch. flow/pre-install is created before the first edit, so a complete revert always exists.
  • Detect the stack. It reads package.json, pyproject.toml, Cargo.toml or go.mod and records the test, lint and build commands you already have. It records your commands; it does not add its own.
  • Install the skill. flow-agent-orchestrator is the only mandatory change to your repo — it is what teaches any agent to read the board, plan epochs, dispatch work and merge.
  • Mount the board and orchestrator, integrated behind your auth or as a standalone panel.
  • Create the dashboard. Metric tables, views and collectors are wired to whatever the project already emits, so the strategy and agent-performance views have data from the first cycle.
  • Configure execution policy — default model, effort, autonomy, verification thresholds and merge policy, all overridable per card.
  • Run a smoke test. Installation is not finished until one real card has travelled from Todo to an open PR under your own CI.
  • Report what it created, what it skipped, and how to remove it.

If a step cannot be satisfied, the agent stops and reports rather than improvising around it.

What it drops into

The goal is that Flow drops into any project and runs on the toolchain that is already installed — JS, Python, Rust, Go, whatever the repo speaks. It adds no runtime dependency and no build step of its own: it discovers your test, lint, and build commands and calls them. An agent already running on your machine should know what to do after one addition to the repo — the flow-agent-orchestrator skill. Nothing else.

Where the orchestrator lives is a separate choice. It can run as a standalone admin panel beside your platform, or be integrated into it. Integrated is the better solution: it inherits your RBAC/ACL — the same users, roles, and permissions — sits on the same database, and shares the general knowledge your platform already encodes, so agents read your domain instead of guessing at it.

The install is one skill plus an agent-executed install.md; the deployment shape is the only real decision. Uninstalling removes the orchestrator, not the work it did — that lives in git like any other commit.

Uninstall

Removal is easy: delete the skill, drop the board routes, drop (or keep) the orchestrator tables. What removal does not undo is the work the agents did — those are ordinary commits in your repo, and the only way to fully revert them is git checkout flow/pre-install.

Test it thoroughly — and be ready to revert Run it on a real but non-critical part of the backlog first, with automerge off, and read the PRs. Keep the snapshot branch until you're satisfied, and revert everything if it isn't working for you. We strongly believe that once you've tried the orchestrator, you won't roll back.
