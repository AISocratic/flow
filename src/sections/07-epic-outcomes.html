07Epic completion & result evaluation

Finishing the tasks is not the same as achieving the result.

Completing every task in an epic does not mean the epic succeeded. When the last task lands, an independent evaluation agent reviews the epic's original intent, the completed tasks and merged PRs, the verification scores and test results, the deployment status, the relevant product or business metrics, and any regressions or incidents that appeared along the way. It then records a completion assessment.

  • Completed successfully — the intended result was delivered.
  • Completed, awaiting metrics — the implementation is finished, but the outcome needs more data before it can be judged.
  • Partially completed — the work shipped, but the intended result was not fully achieved.
  • Needs improvement — the evaluator creates a follow-up epic.
  • Invalidated — the underlying assumption was wrong, and the project itself should be reconsidered.

When improvement is required the evaluator creates a new epic or proposes a change to the project. It does not silently reopen completed tasks — an epic that stays permanently open because optional improvements were discovered tells you nothing about whether the original intent was met.

Two separate controls Task verification asks whether the implementation satisfies the card, and it runs before merge. Epic evaluation asks whether the completed body of work achieved its intended result, and it runs after all the work is done and — where the card's completion policy requires it — after deployment metrics have arrived.
