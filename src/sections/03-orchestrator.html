03Workflow Graph / Agent Orchestrator

A third board view that is the execution plan.

Board and List answer what is on the plate. Workflow Graph answers in what order it can run — and it is the same structure the orchestrator executes, not a drawing of it. Every epic renders as its own self-contained DAG (nodes are tasks, edges are dependencies) laid out against a shared ready-wave axis, so horizontal position is execution order rather than layout aesthetics. Task edges never leave their epic: an epic graph is complete on its own, which is exactly what lets the orchestrator dispatch one wave of one epic without reasoning about the rest of the board. The only place two epics touch is the project layer, drawn here as the left-hand rail — a project-level edge from epic A to epic B is a gate, and when it opens, B's whole graph becomes ready and therefore starts further right on the wave axis.

Node fill is card state — grey done, green an agent is running it, amber waiting on a dependency. Epic A occupies waves 1–3; epic B is gated by A at the project layer, so its own wave 1 lands on the board's wave 4; epic C shares no edge with either and starts immediately.

  • The ready set is a column. Everything in the leftmost unfinished wave of an epic is dispatchable right now — that is the orchestrator's next wave, read straight off the chart instead of inferred from a plan.
  • Critical path is visible. The longest chain inside an epic graph is that epic's floor on wall-clock; adding agents widens the columns, it never shortens the chain.
  • "Why isn't this running?" is one hop. An amber node either waits on siblings you can see, or on the single project edge feeding its epic card.
  • Epics stay independently schedulable. Because no task edge crosses the boundary, an epic can be re-planned, paused, or re-run without recomputing any other epic's DAG.
Write-time validation A task dependency is accepted only when both cards resolve to the same parent_id epic; a link drawn between two epics is stored as a project-level gate on the epic cards, and a dep that would close a cycle is refused outright. Every rejection lands in the card log with its reason, so the graph is a DAG by construction rather than by nightly repair.

Executing it

An agent picks its own scope: a whole epic, or a few tasks inside one. Both are safe precisely because the epic graph is self-contained — taking the epic means owning its waves end to end; taking a slice means claiming individual cards out of the current ready wave and leaving the rest of the graph to whoever else shows up. The orchestrator walks each epic graph, takes the leftmost unfinished wave, and dispatches one agent per card into its own git worktree. It is harness-agnostic: each card goes to whichever coding agent its policy names (Claude Code, Codex, or an API-driven worker). Approved-but-unmerged PRs are merged first on every cycle, so finished work never queues behind new work — and merging is what clears the deps that promote the next wave.

Claiming a card

Before touching anything, an agent assigns the card to itself and then moves it to in progress. That column move is the signal — it is how every other agent (and every human watching the board) learns the card is taken. A card carries one worker in practice, but the assignment field holds two, so a race is recorded rather than lost. When two workers land on the same card, the one with the lowest claim timestamp decides: keep the card, or leave it to the other agent. The decision is explicit and logged; nobody silently steals work, and no card ends up with two agents editing it.

  • Assign, then move. Self-assignment and the move to in progress are one atomic step; an agent that can't do both doesn't start.
  • Two slots, one worker. The second slot exists to make contention visible — it is never a licence for two agents to work the same card.
  • Earliest claim arbitrates. Lowest timestamp holds the decision right, which makes the outcome deterministic and replayable from the log.
  • Stale claims expire. A worker that stops heartbeating loses its slot, and the card returns to the ready wave rather than sitting occupied.

Agent signaling — TBD

The board covers status signals well: claim a card, move a column, comment on a card, and everyone converges on the next poll. What's still open is agent-to-agent signaling — pushing updates, changes, and notifications between running agents without round-tripping through the board: "I changed the shape of this module", "my card is going to break yours", "stop, I've already fixed that". Polling a card log is a poor substitute for a message bus.

Open question Design a signaling channel for live agents — delivery, ordering, and who is allowed to interrupt whom. Action: ask @dan van flyman about Synapse before we build anything here; it may already be the answer.
Note — we don't build the harness We're not trying to improve the harness — many teams are already working on that. Instead, our orchestrator delegates work to the existing harnesses, which serves two purposes:
  1. we use our subscription tokens, saving money;
  2. we take advantage of the existing harness — the system improves as the harness improves.
