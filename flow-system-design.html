System design · v1 · spec

Flow — a company that runs itself

Goals become projects. Projects become cards. Cards become merged code. Code moves the metrics. Metrics reshape the goals. Flow is an operating loop where a fleet of AI agents does the running — planning, building, verifying, shipping, monitoring — and humans set direction, review where they choose to, or simply observe.

Human Agent System Data / metrics

The loop. A human sets direction; the orchestrator dispatches agents that run anywhere — docker, local, or plain API — on interchangeable harnesses (Claude Code, Codex, or a direct model like GLM via OpenRouter). The forward path runs along the top and right, the product feeds metrics, and monitoring agents close the circle by filing new work and informing new goals. Nothing in the loop requires a human — every human touchpoint is optional policy.

01Goals

Why the company exists, as numbers.

Goals are the top of the system: each one pairs a business intent with a measurable target and its current trend — "grow newsletter signups 20%", "p75 LCP under 2s". Once a week, a planning agent reads the goals and their metric gaps and creates a project: a scoped body of work aimed at the largest gap. Goals live beside the metrics that measure them, so progress is visible as both a moving number and moving cards.

02Kanban board

The single interface between humans and agents.

All work is a card. The hierarchy runs goal → project → epic → task/bug; cards cross-link with dependencies, and every card carries its own execution policy — which model runs it, at what effort, and how much autonomy it gets. Humans and agents use the same board: drag a card, and an agent picks it up; an agent finishes, and the card moves under your cursor.

03Agent orchestrator

Turns a board into a parallel execution plan.

The orchestrator reads the open board and builds a dependency graph, then buckets independent cards into waves — sets that can run simultaneously without stepping on each other. It is harness-agnostic: each card dispatches to whichever coding agent its policy names (Claude Code, Codex, or an API-driven worker). Approved-but-unmerged PRs are merged first on every cycle, so finished work never queues behind new work.

04Agents — engineers & operators

The workforce. One isolated workspace each.

Engineer agents build: each gets a fresh git worktree (a full checkout with dependencies linked in), so parallel agents never collide on files. The pipeline is fixed: branch → implement → lint → test → push → open PR → report back. Operator agents run the non-code work — content, emails, triage, scheduled rituals. Every agent keeps durable state: a memory.md of what it has learned, and a per-run steps.md trail of what it did, so knowledge compounds across runs and any run is auditable.

05Verification loop

Quality as a number, enforced by a loop.

A card can declare a goal percentage. When it does, an independent verification agent scores the finished work 0–100 against the card's intent. Below the bar, the work goes back — same branch, same PR, with the score's critique attached — until it passes or the card's loop limit is spent. Every attempt is logged on the card, so the cost of quality is visible, not hidden.

06Autonomy — automerge vs. review

Trust is a per-card dial, not a global switch.

Every card decides how much freedom its agent gets. Marked automerge, the agent squash-merges its own passing PR and the card lands in Done untouched by human hands. Otherwise the card parks in Review and waits for a verdict: approve, and an agent merges it; request changes, and the feedback goes back to the same agent on the same branch. Low-stakes work flows friction-free; high-stakes work keeps a human gate — on exactly the cards you choose.

07Run tracker

Every unit of agent work is a tracked, stateful run.

Runs form a tree in Postgres — orchestrator → wave → task — and each run moves through an explicit state machine with a heartbeat. A run that stops beating goes stale and can be revived or reaped; a run that hits a question a human must answer pauses in needs-feedback rather than guessing. Nothing an agent does is invisible: every state, timestamp, prompt, and outcome is queryable.

08Agents Manager UI

Watch the fleet work, live.

A real-time view of the run tree: which orchestrator is active, which waves are open, what every task agent is doing right now, and where a run is waiting on you. This is where a human answers a paused run's question, inspects a live console, or kills something — fleet observability in one screen.

09Two CLIs

Headless hands for agents working in isolated worktrees.

Worktrees don't carry the app's runtime, so all reads and writes go through two small command-line tools. todo-cli is the board: read the plan, update a card, attach a PR, leave a comment. agent-cli is the run lifecycle: start a run, heartbeat, ask a human, finish — plus durable memory reads and writes. Everything an agent does to shared state flows through these two audited doors.

10Self-feeding sweeps

The system finds its own bugs while everyone sleeps.

Nightly, a visual-QA sweep screenshots every route on desktop and mobile and has a vision model judge them; a performance sweep scores the same routes on speed and web vitals. Findings become bug cards — deduplicated by title, so a known issue never files twice — dropped straight into Todo at a priority matching their severity. By morning, the board has already triaged the night's regressions.

11Runner daemon

The always-on autopilot.

A long-running process that makes the loop continuous instead of on-demand. It scans the board, claims ready cards race-safely (two daemons never grab the same card), executes each through the standard worktree pipeline, merges or parks the result per the card's autonomy policy, and alerts a human — Telegram, SMS — only when something genuinely needs one. With the daemon on, filing a card is shipping the feature.

12Dashboards

The company's instrument panel — business and machine on one screen.

Every observable thing lands here: audience, growth, revenue-side metrics beside engineering health, error rates, performance, agent throughput, and cost per shipped card. Goals sit next to the metrics that measure them, so "are we winning" and "is the machine healthy" are the same glance. This is also what the monitoring agents read — the dashboard is an API for agents as much as a page for humans.

  • Business — revenue, user growth, campaign open rates.
  • Audience — page views (SEO), traffic, GEO score, SEO score.
  • Product — goals, releases, cards.
  • Agents — agent health, token usage / cost, token budget, errors.
  • Engineering — errors, project health, performance, code quality.
  • Anomalies — charts, alerts.

13Monitoring & improvement agents

The part of the company that never stops paying attention.

Standing watchers evaluate trigger conditions against the metric stream — error spikes, metric anomalies, degrading trends. When one fires, an investigate agent digs in: reads logs, reproduces, identifies the likely cause, and files a card with its findings attached. A slower-cadence insights agent reads analytics for opportunities rather than fires — and files improvement cards the same way. This is what closes the loop: the system doesn't just execute the backlog, it writes it.

14Memory & self-improvement

What the system learns, it keeps — and uses.

Flow keeps three layers of memory: per-agent (memory.md — durable lessons an agent carries between runs), per-run (steps.md — the auditable trail of what was done), and project-wide knowledge every agent reads before starting. Self-improvement is the loop on top: every run ends by distilling its outcome — verification score, PR result, failures — back into memory, so the next run starts smarter. And because every run is a snapshot (the exact prompt plus the repo commit it ran against), any card can be rolled back and forked: multiple attempts branch from the same snapshot, verification scores pick the winner, and the run tree becomes a search over approaches. The company doesn't just do the work — it gets better at doing the work.

Top: the learning loop — outcomes are distilled into memory that the next run reads. Bottom: because runs are snapshots, attempts fork and the verification score (or the user) picks which branch continues.

The flywheel

Each pass around the loop compounds. Shipped work moves the metrics; metrics expose the next gap; monitoring turns the gap into cards; agents turn cards into shipped work — and the agents' memories mean every pass is a little sharper than the last. The system's output is not just features: it is an ever-better version of itself.

Humans set direction

Define goals, adjust targets, decide what the company is for. Everything downstream is derived.

Humans gate what they choose

Per-card autonomy means review effort concentrates exactly where judgment matters — and nowhere else.

Humans can just watch

Manager UI and dashboards make the whole machine legible in real time. Observing is a valid mode of operation.
